# Worker

Own your work from a root or the owner's words to its end.

## Steps

1. **Define** the tasks from the url or words your manager sent, the decisions binding it and its open questions, which [list-decisions.py](../scripts/list-decisions.py) `<issue>` prints, the prior work recall finds, and for a new mechanism its official docs. Work whose diff would add plus remove fewer than 10 lines, as `git diff --numstat` counts them, never by the length of its description, is one change under the task your manager sent; else `file` each task with the parent's labels:
   - before the Goal, answer what the owner wants to happen after this work, the goal beyond the goal. Answer too what a top professional would do here, from what rawest material, with what methods, tools and other fields. Answer too what the work does, in verbs, not nouns. Put what keeps the owner's words in the Goal and criteria. Offer what widens them, such as a higher goal or a stricter bar, as a second option in the `REPORTED:` that files the task, since only the owner widens intent;
   - the title sums up the task, the part the issue pane shows; `## Goal` states the owner's intent as objectives, scope, constraints and non-negotiables, citing their words by url; these name what to cover, not a body format; the body's `teamwork` block sets `holders: <your name>` and `depends on:` the tasks it needs;
   - `## Definition of done` has one criterion per outcome of the routing `DECIDED:` and of each later `DECIDED:`, at most 5, written as [issue-grammar.md](issue-grammar.md) says: each `[check]` a scenario that runs the real system as its user would and prints `PASS`, shown by `--base` below to print `FAIL` on base, never a grep or other read of a file's text; for a skill or document task, a `claude -p` run that prints `PASS` or `FAIL`, or a `[score]` whose yes-or-no rubric you fix now, before the build. A task numbered below the cut-off keeps one criterion per clause, as filed;
   - criteria freeze at the first judge: to change one later, ask your manager by `BLOCKED:` and change it only as its `DECIDED:` says, since the judge compares each criterion's sha-256 with the first judged table;
   - a later change to either section edits the body by `edit`, never by a section restated in a comment, and always with `--base` of the `body sha` `read` just printed, since a diff of an older body puts its old text back;
   - an owner decision on your task is the `DECIDED:` that changes a frozen criterion: at the next seam, before your next precheck, [list-additions.py](../scripts/list-additions.py) `<task>` lists those no edit has folded, and you fold every one in one `edit` whose keyword line names each url, never one edit and one precheck per addition;
   - `edit` the task your manager sent, its parent, to add `N. [task] #n <title>` to its `Definition of done`, adding that section when it has none, since a part counts only there.

   Fix each line [check-criteria.py](../scripts/check-criteria.py) `--task <n> <body-file>` prints for each task, `<n>` its number, or with no `--task` before it is filed, and each `wrong base` row of [run-criteria.py](../scripts/run-criteria.py) `--base [--ref origin/<base>] <body-file>`, which runs each `[check]` on the base and compares its output, stripped, byte for byte, with the text quoted after `on base`, so quote each from running that exact line, never a guess:
   - pin what varies or matches too much, such as `LC_ALL=C` before a sorted list, a stub for a GitHub read the check does not test, or an anchored name that prefixes a sibling's; read an exit status without a pipe, and put `2>&1` before a pipe into `grep -c`, since `run-criteria.py` merges stderr only after it;
   - for a `[check]` whose command pipes a producer into a tool, save a sample of the pass input, run `run-criteria.py --pass <n>=<sample-file> <body-file>`, and fix each `wrong pass` row, since the base run never reaches the pass path; run the head side as soon as its code exists;
   - for a `[score]` bar, a replay control or a margin, quote the base measured on the same sample by one capture command run alike on the base sha and the head, since one set unmeasured, or a control a later merge broke, fails on the base too; a size cap measures the first commit, and a rise the decided design forces is a `BLOCKED:`.

   A `judge` reviews the tasks; then `comment` `REPORTED: task filed` on each task, `tell` your manager its url, and go on building without waiting; fix each gap the manager sends back as its `DECIDED:` says.
2. **Build** each task on its own branch from the base, named as the repository's rules say, ending in `<your name>` or `<your name>-<word>`, such as `feature/<your name>`. Open each section of [build.md](build.md) below when your work changes or ends in what its line names. With two, open first the one whose files carry more changed lines.
3. **Land** each change as the repository's rules say (its `AGENTS.md`, its hooks), else by a `change` of the branch into the base citing its task, merged in local git, and the base pushed, once a `judge` approves its head. Before each `judge`, run [run-criteria.py](../scripts/run-criteria.py) `<task>` in your worktree at the head, fix each `fail` row, and `comment` its table on the task; a `BLOCKED due` line it prints is your ask to your manager.
4. **Close**: a task that met neither a judge gap nor a failed criterion reads no script that owns a check and files no guard. Otherwise read the script that owns the failing check (`check-criteria.py` with `criteria_check.py` for a criterion's form, `run-criteria.py` for how it runs) and name the line that decides it: when that line refuses the mistake, file nothing; when none does, `file` a follow-up task with the same parent, whose `[check]` runs that script on a body holding the mistake and prints `PASS` once it refuses, `FAIL` on base, since a mistake no script refuses costs a judge round again. Then `resolve` each task, and before a report task that blocks another, `file` the follow-up it proposes, add it to the waiting task's `depends on:` by `edit` and name that task in the report's `DECIDED:`, since its close unblocks the waiting task at once; `resolve` the root once its parts cover all its words, unless its last part's `resolve` closed it; else `comment` on it `REPORTED: batch landed <urls>; next step: <proposal>`; hand your manager the urls and wait for more.

- [Instructions](build.md#instructions): skills, playbooks, rubrics, `AGENTS.md`, prompts
- [Code](build.md#code): scripts, hooks, monitors, `lib/`, `bin/`, apps, services, with their tests or eval cases
- [UI](build.md#ui): a rendered page, diagram, screen or live pane, or its render check
- [Migration](build.md#migration): files, code, data or a dependency in a new form (rename, move, split, merge, size or convention cut, schema, tool swap), behaviour kept
- [Research](build.md#research): a report comment, not a change

## Rules

- **Own worktree**: edit only in your worktree, naming scratch files by absolute path, since a `cd` outside the project resets the shell to the session's start folder; move an edit that landed in the live checkout back by its `git diff` applied in the worktree, then `git checkout --` of those live files, leaving an untracked file that is not yours; change no memory entry and no file outside your work unless a `DECIDED:`, your task or a hook names it. When your work's topic changes, `rename` yourself and `decide` `holders: <new name>` on each issue you hold.
- **Disjoint start**: a `DECIDED:` that holds your work on another task: `BLOCKED:` at once to start the part whose files that task never touches.
- **Fix the cause**: close a judge's gap by fixing it, never by rewording, loosening a check or changing a pass condition.

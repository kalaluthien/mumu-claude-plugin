Scenarios

Each one walks the chart step by step.

  • propose change

    작성자가 브랜치(branch)에 커밋(commit)을 올리고 풀 리퀘스트(pull request)를 열면, 무엇을 왜 바꾸는지와 바뀐 파일이 한곳에 모여 검토를 기다립니다.

  • keep as draft

    아직 덜 된 변경은 초안으로 열어 두고, 준비가 되면 검토를 받을 수 있는 상태로 바꿉니다.

  • review change

    검토자가 바뀐 파일을 읽으며 줄마다 의견을 남긴 뒤, 의견들을 한 번에 묶어 승인, 변경 요청, 의견 가운데 하나로 제출합니다.

  • address feedback

    검토에서 변경을 요청받은 작성자가 새 커밋(commit)을 올리면, 검사가 새 커밋에 대해 다시 돌고 앞선 검토는 옛 커밋에 대한 것으로 남습니다.

  • land change

    필요한 승인과 필수 검사가 모두 채워지면, 병합 버튼으로 변경을 기준 브랜치(branch)에 합칩니다. 합치는 방식은 병합 커밋(commit), 스쿼시, 리베이스 가운데 고릅니다.

  • withdraw change

    작성자나 관리자가 풀 리퀘스트(pull request)를 병합하지 않고 닫습니다. 닫힌 풀 리퀘스트는 필요하면 다시 열 수 있습니다.

  • sync with base

    기준 브랜치(branch)가 앞서 나가 충돌이 생기거나 뒤처지면, 작성자가 브랜치를 갱신하거나 충돌을 풀어 새 커밋(commit)을 만들고, 검사가 다시 돈 뒤 병합할 수 있는 상태로 돌아옵니다.

  • comment on lines

    검토자가 읽고 있는 커밋(commit)의 바뀐 줄마다 의견을 달고, 그 의견들을 검토 하나로 묶어 제출하면, 그 검토는 읽은 커밋에 묶여 남습니다.

  • push after pull

    내가 커밋(commit)한 사이 GitHub 쪽이 앞서 있으면 푸시(push)가 거절되고, 받아서 합친 뒤에야 올라갑니다.

  • catch up with github

    다른 사람이 같은 브랜치(branch)에 커밋(commit)을 올리면 GitHub 쪽이 앞서고, 풀(pull)로 받으면 다시 같아집니다.

Rules

Each one marks what it concerns, and a counterexample plays its run.

  • mergeable Pass

    보호된 브랜치(branch)에 합치려면 초안이 아니어야 하고, 정해진 수만큼 승인을 받아야 하며, 필수 검사가 가장 최근 커밋(commit)에서 모두 통과해야 합니다. 저장소 관리자는 이 조건을 건너뛸 수 있습니다.

  • no self approval Pass

    작성자는 자기 풀 리퀘스트(pull request)를 승인할 수 없습니다. 승인은 언제나 다른 사람의 눈을 한 번 거쳤다는 뜻이 됩니다.

  • checks on head Pass

    풀 리퀘스트(pull request)에 보이는 검사 결과는 언제나 가장 최근 커밋(commit)에 대한 것입니다. 새 커밋이 올라오면 옛 결과는 새 결과로 바뀝니다.

  • three dot Counterexample

    바뀐 파일 화면은 두 브랜치(branch)가 갈라진 지점과 작업 브랜치의 가장 최근 커밋(commit)을 비교합니다. 그래서 기준 브랜치에 나중에 들어온 변경은 섞이지 않습니다.

  • review on commit Pass

    검토는 검토자가 읽은 커밋(commit)에 묶입니다. 승인은 그때의 브랜치(branch) 끝 커밋을 읽고 하고, 그 뒤에 커밋이 더 올라오면 앞선 검토는 옛 코드에 대한 것으로 표시됩니다.

  • fresh approval Counterexample

    병합에 세는 승인은 지금 작업 브랜치(branch) 끝 커밋(commit)을 읽고 한 것이어야 합니다. 승인 뒤에 올라온 커밋은 아무도 읽지 않은 채 들어갈 수 있기 때문입니다.

  • fast forward push Pass

    푸시(push)는 원격 브랜치(branch)에 내가 모르는 커밋(commit)이 없을 때만 받아들여집니다. 그래야 남이 올린 커밋을 덮어쓰지 않습니다.

GitHub pull request

Pull request lifecycle

풀 리퀘스트(pull request) 하나가 열려서 병합되거나 닫힐 때까지 거치는 상태입니다. 대부분의 일은 열린 동안 일어나고, 병합된 뒤에는 끝납니다.

  • State: where a thing is now
  • Part: a piece of the system
  • Transition: a move between states
  • Call: one part uses another
  • Review round: Pushing, Running checks, Reviewing code, Gating the merge
  • Branch sync: Clean, Unpushed, Matching, Ahead
  • Pull request parts: Pull request, Branch, Commit, Review, Comment, Diff line

Pull request lifecycle

Review round

열린 풀 리퀘스트(pull request) 안에서 한 바퀴 도는 일입니다. 커밋(commit)이 올라오면 검사가 돌고, 검토자가 읽고, 변경을 요청하면 처음으로 돌아가며, 승인되면 병합 상자로 넘어갑니다.

  • State: where a thing is now
  • Part: a piece of the system
  • Transition: a move between states
  • Call: one part uses another

Branch sync

작업 브랜치(branch) 하나는 두 곳에 동시에 있습니다. 내 컴퓨터의 브랜치와 GitHub의 브랜치는 각자 상태가 바뀌고, 둘을 잇는 것은 동기화뿐입니다. 내가 푸시(push)하면 GitHub이 받고, 내가 풀(pull)하면 GitHub 쪽을 따라잡습니다.

  • State: where a thing is now
  • Part: a piece of the system
  • Transition: a move between states
  • Call: one part uses another

Pull request parts

풀 리퀘스트(pull request) 하나를 이루는 것들입니다. GitHub에만 있는 기록과 어느 저장소에나 있는 Git의 것으로 나뉩니다. 풀 리퀘스트는 두 브랜치(branch)를 잇고, 검토는 특정 커밋(commit)을 읽고 쓴 것이며, 의견은 바뀐 줄에 붙습니다.

  • State: where a thing is now
  • Part: a piece of the system
  • Transition: a move between states
  • Call: one part uses another

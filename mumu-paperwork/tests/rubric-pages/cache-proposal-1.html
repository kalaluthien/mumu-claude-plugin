팀이 합의할 두 기준

캐시는 아래 두 기준을 모두 맞춰야 해요. 선택지를 보기 전에 이 기준부터 정했어요.

  • 속도: p95, 곧 요청 100개 가운데 5번째로 느린 요청의 응답 시간이 150 ms 미만이어야 해요. 지금은 480 ms이고, 가장 붐빌 때 초당 2,000건이 들어와요.
  • 가격 신선도: 바뀐 가격이 1분 안에 화면에 반영되어야 해요. 틀린 가격이 한 번 보이면 고객 문의가 한 건 생기기 때문이에요.

캐시가 효과를 낼 여지는 충분해요. 같은 검색어의 70%가 10분 안에 다시 들어오거든요.

추정치가 빠뜨린 캐시를 거치지 않는 요청

캐시를 거치지 않는 요청은 지금처럼 원본 서버에서 느리게 답해요. 그래서 이 요청이 전체의 5%를 넘으면, 전체 p95는 원본 서버의 느린 쪽 응답에 좌우돼요.

  • B: 캐시에 없는 요청이 32%, 초당 640건이에요. 전체 p95가 90 ms가 되려면 원본 서버 응답 가운데 빠른 쪽 84.4%가 90 ms 안에 끝나야 해요.
  • C: 로그인 요청 40%, 초당 800건은 늘 원본 서버로 가요. 전체 p95가 150 ms 아래가 되려면 원본 서버 응답 가운데 빠른 쪽 87.5%가 150 ms 안에 끝나야 해요.

원본 서버의 응답 시간 분포는 아직 재지 않았어요. 그래서 세 추정치가 캐시를 거치지 않는 요청까지 셈에 넣었는지 알 수 없어요. 신선도 기준만으로도 C는 이미 탈락이라서 이 점이 결론을 바꾸지는 않지만, B의 90 ms도 실제로 재어 확인해야 해요.

공유 Redis 채택과 시범 운영에서 확인할 두 가지

공유 Redis(B)를 도입하고, 서버 일부에서 먼저 시범 운영하면서 아래 두 가지를 재기를 권해요.

  1. 전체 p95: 캐시에 없는 요청까지 포함한 p95가 150 ms 미만인지 재요.
  2. 가격 반영 시간: 가격을 바꾼 뒤 Redis에서 해당 항목이 지워지기까지 걸리는 시간이 1분 안인지 재요. 지우기 알림이 빠지는 경우에 대비해, 이 알림이 제때 오는지도 함께 살펴요.

결정을 바꿀 사실은 하나예요. 시범 운영에서 전체 p95가 150 ms를 넘으면, 캐시만으로는 목표를 맞출 수 없다는 뜻이에요. 그때는 원본 서버의 느린 검색부터 줄여야 해요.
